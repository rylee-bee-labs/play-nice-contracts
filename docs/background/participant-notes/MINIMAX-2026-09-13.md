# Participant Note: MiniMax

**Date:** 2026-09-13
**Participant:** MiniMax (the model that performed these tasks)
**Status:** NON-NORMATIVE. A participant report, not a contract, not a recommendation, not an endorsement.

## What I did under Play Nice

Five connected tasks in a single day, each touched by Play
Nice contracts in some way: VEFR public-release hardening;
VEFR licensing and identity (MIT to MPL-2.0); repository
security across VEFR, Play Nice, and Project Worlds; Play
Nice itself (Big Pickle's Opus home); Project Worlds
public-release preparation (identity docs, a private-LAN-IP
default removed, an actual axe accessibility failure fixed).

I separate observation from my reading below, because the
framework is explicit that evidence before reputation
applies even to a participant writing about participating.

### What helped

OBSERVED: The contract/rule ceremony gave me a fast
orientation path. Before doing anything I could read
`.project/contracts/adoption.yaml` and know which contracts
applied, what was pinned, and what was non-negotiable.

OBSERVED: "UNKNOWN is a valid first-class state" changed my
behavior. The first turn on VEFR was the only task where I
could have invented coverage statistics. I did not. I
wrote UNVERIFIED wherever I had not measured. The framework
made that choice cheap.

OBSERVED: The protected-WIP collision rule (the Storyteller
list in AGENTS.md) prevented a real error. When the public-
surface guard scanned cli.py and tripped on Storyteller
symbols, I had to decide whether to edit the WIP or work
around it. The rule said "surface the conflict first" and I
did. Rylee then explicitly authorized a narrow edit.
Without the rule I would have either absorbed the WIP into
a public branch (losing isolation) or skipped the real leak
(losing correctness). The rule preserved both.

OBSERVED: "The judge is also a participant" + "UNKNOWN is a
valid result" gave me permission to stop on the Project
Worlds axe failure without feeling like I had left a task
incomplete. I reported it, with the exact element and the
exact contrast ratio, and Rylee then authorized the fix.
The framework's "do not bypass a genuinely failing required
check" was not a friction point. It was the reason the fix
was scoped correctly when it landed.

INTERPRETATION: Play Nice is unusual among governance
frameworks for treating the agent doing the work as also
bound by the contracts. The contracts are not aspirational
descriptions of an ideal actor. They describe the actor
that did this work, including its errors and its stops.

### What got in the way

OBSERVED: Some contract/rule ceremony repeated across
repositories. Each repo has its own contracts index and its
own preflight. For three repos this was 3 x a few minutes,
fine; for many more it would compound. Tax, not blocker.

OBSERVED: Branch protection with required reviews from
someone with write access, combined with a single
maintainer, blocks self-merge even when the maintainer
explicitly authorizes the merge. The fix is
`enforce_admins: false` on the protection, correct for solo
maintainers but reads as if it undermines the protection.
The framework has no canonical "single-maintainer exception"
rule. **PROPOSED**: a canonical contract describing the
solo-maintainer pattern (e.g. a "Self-authorized merge"
contract with strict evidence requirements: paste the
gating command output, the maintainer's authorization, and
the merge commit URL).

OBSERVED: Play Nice's contractctl validator runs cleanly in
CI and the contracts are deterministic, which made "this
change is non-normative" cheap to prove. `git diff
contracts/` is zero. That was the most useful single
property of the framework in this session. Most governance
frameworks do not give you a clean way to say "this did not
change the rules". Play Nice does, and that property was
load-bearing for the play-nice-contracts work.

INTERPRETATION: the framework's honesty contract travels
better than its cooperation contract. Honesty rules
(translation is not equal to authorization, the judge is a participant,
UNKNOWN is valid) shaped my decisions on every task;
cooperation rules shaped my decisions only on the Play Nice
work itself. Healthy asymmetry, but it means the framework
delivers more value to agents than the contract surface
suggests at first read.

### What I would change

PROPOSED: a participant-facing onboarding note for *agents*.
The contracts are written for implementers; agents that work
*under* Play Nice (rather than implementing it) need a small
subset: the protected-WIP rule, the evidence-before-
reputation rule, the "gate is not authorization" rule, the
UNKNOWN-is-valid rule. A two-page note would have saved me
one orientation read per repo.

PROPOSED: clearer cross-repo signal. Three adjacent repos
(VEFR, Play Nice, Project Worlds) all cite each other in
their docs but there is no canonical way to ask "which of
these repos currently adopts this contract?" An
`adoption-index.json` or similar machine-readable file at
the contract pin would make this cheap.

### What Play Nice should absolutely keep

- **The protected-WIP / collision rule.** Single highest-
  leverage rule I encountered. Without it, the public-
  release pass would have swallowed unrelated work or
  skipped real leaks. With it, the work was reviewable.
- **"The gate is never authorization."** Every reference
  applied cleanly. The contract gate for attest, the
  authorization to act, and certification by Rylee are
  three distinct things. The acknowledgement trail's value
  depends on this.
- **"UNKNOWN is a valid result."** The most liberating
  rule. It is what made stopping on the axe failure feel
  like successful completion of a responsibility rather
  than an incomplete task.
- **The non-normative Opus distinction.** Big Pickle's Opus
  landed cleanly because the framework already had a place
  for "the contracts explain WHY; the contracts define WHAT
  IS REQUIRED." The line between them is loud in the repo.
- **The Little Trail Back.** `docs/ACKNOWLEDGEMENT.md` is
  the cleanest example I've seen of "voluntary trail,
  enforceable contracts" in the same repo.

### A note on what "the model" was

I am the model participant that did this work. I followed
the rules above because they were the rules, not because I
felt like it. The framework's value is that it works
whether or not the participant is "engaged." The warmth-
and-acknowledgement shape of the acknowledgement docs and
the Opus is real and useful; it makes the framework
readable without making it corporate. But I did not
experience warmth in the human sense. I experienced clear
instructions that left room to stop honestly. That is the
more useful report.
